---
name: Zyla YouTube downloader engine
description: Operational facts about the paid ZylaLabs download engine that sources YouTube video for the clip pipeline
---

- The clip pipeline sources YouTube video through the user's PAID ZylaLabs "YouTube Download and Info API" (`ZYLA_API_KEY` secret): resolve a direct R2 mirror URL first, then probe/loudness/section-download all read from that mirror; any failure falls back to the yt-dlp → Railway → Vercel → Cobalt chain. Only start calls consume monthly quota; progress polls and R2 links are free.
- **Zyla's `progress_url` is NOT on zylalabs.com** — live responses point at third-party infra (observed `youtube-api-progress-*.up.railway.app`). Host-pinning it to zylalabs.com broke every real start while unit tests stayed green (fixtures matched the pin, not reality). Validate SSRF properties only (https, public host); never pin their unstable hostnames. After hardening external-API validation, always re-run one LIVE call.
- **Unit tests must never see the real key**: the workspace env exports ZYLA_API_KEY, and queue/clip tests post fake YouTube URLs by the dozen — without the vitest setup file stripping the key, tests fire real paid starts and get flaky from network latency.
- Live testing burns quota — prefer already-finished url+format pairs (`cached:true`, zero cost). WARNING (Aug 16 2026): old demo video `LXb3EKWsInQ` now FAILS on Zyla's engine at BOTH 1080 ("download_error") and 720 ("internal_error" after downloading ~65%) — it is no longer a smoke test. Use `dQw4w9WgXcQ`@720 (finished in ~12s live) to verify the engine/key/quota.
- Engine failures are often VIDEO-specific and sometimes format-specific. The clip resolver ladders 1080→720 ONCE on a conversion-level failure (never on timeout — the finish-watcher owns that — and never on start-level auth/quota errors) and aliases BOTH format cache keys to the served URL, so repeat requests don't re-burn a start that will fail the same way. Downstream ffprobe quality gates stay honest about real dimensions.
- Resolved mirrors are cached durably in Postgres (`zyla_cache`, ~6-day TTL, July 2026) — restarts/republishes and sibling autoscale instances reuse ONE paid start per video+format. Lessons: liveness-check a durable link (ranged 1-byte fetch) before trusting it — mirror links can die early; deletes must be conditional on the stored URL or a stale delete clobbers a concurrent fresh write from another instance; ytDownload unit tests MUST mock the cache module or they write fixture rows into the real dev DB.
- Warm-on-paste: the UI pings the server the moment a YouTube link is pasted, so the engine converts during the user's configure time. In-flight dedupe + the durable cache keep it to one paid start no matter how often it fires; a per-user rate bucket guards paste-spam quota burn.
- Per-caller poll budgets: the poll fn + resolver take a caller timeout budget — public routes keep 240s and clip source prep defaults to 3 min (overrideable). Timeout is CALLER state, not job state: the exact timeout error text doubles as a resurrect marker, so a longer-budget caller revives a job a shorter-budget poller already "failed". Resolver loops must not treat a timeout-marked shared job as terminal while their own budget remains. After a YouTube metadata bot-check races an in-flight warm conversion, give that same deduped job a bounded 90-second recovery wait before using public fallbacks; this avoids false cookie errors without making the UI look stuck.
- Timeout ≠ wasted paid start: a detached finish-watcher polls an abandoned conversion to completion (20-min cap; unref'd timers so it can't hold shutdown open) and writes memory+durable caches — the next retry is instant and free. Job lookup JOINS timeout-failed jobs within the watch cap instead of buying a duplicate conversion.
- Inflight-map deletes must be identity-guarded: a stale actor (expired watcher, old poller) deleting the key unconditionally clobbers a REPLACEMENT start's entry → a third paid start. Delete only when the entry still resolves to the same jobId.
- Failure notes (per-videoId, 15-min TTL) record WHY the engine failed (quota/auth/not_configured/timeout/engine_failed); the final clip error leads with that reason and gives cookie advice only when the engine didn't fail. Notes are video-level and mildly stale by design; every success path clears them.
- Dedupe is process-local by design (single VPS process); the durable cache covers restarts. A cross-instance DB lease was evaluated in review (Aug 2026) and deliberately skipped as over-engineering for the current single-instance deployment.
- Cookie tests + the dev server share `/tmp/clipai-cookies` unless `CLIPAI_COOKIES_DIR` is set — parallel vitest workers raced each other and wiped the server's live cookies.txt until the setup file gave each worker its own dir.

- For a resolved Zyla media mirror, cut clip sections with ffmpeg’s direct HTTP input first, not yt-dlp’s generic `--download-sections` extractor. **Why:** the generic extractor can stall for minutes on an already-resolved object; ffmpeg seeks the media stream directly. Keep yt-dlp only as a bounded compatibility fallback.
